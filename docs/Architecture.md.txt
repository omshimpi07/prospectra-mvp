# Prospectra

## Architecture Specification v1

### MVP — Free-First Prospect Intelligence Platform

---

# 1. Architecture Goal

Prospectra is a prospect-intelligence system that helps service sellers discover, research, qualify, and prioritize local-business prospects.

The architecture must optimize for:

* simplicity
* correctness
* evidence
* maintainability
* low operating cost
* provider independence
* fault isolation
* gradual extensibility

The MVP should remain a **modular monolith**, not a distributed system.

Core philosophy:

> **Deterministic software executes. AI interprets. Humans decide.**

---

# 2. System Boundary

Prospectra MVP begins with:

```text
Seller
  ↓
Sales Target / ICP
```

and ends with:

```text
Evidence-backed prioritized prospects
  ↓
Human review
```

Optional selected-prospect research extends the boundary to:

```text
Prospect
  ↓
Deep Research
  ↓
Research Summary / Talking Points
```

The MVP does not cross into autonomous outbound communication.

# 4. Architectural Style

## Decision

Use a:

**Modular Monolith + Asynchronous Job Processing**

This means:

* one backend application
* one primary database
* one worker application/process
* clearly separated internal modules
* explicit interfaces between major components
* asynchronous processing for long-running workflows

The backend is logically modular even though it is physically deployed as a small number of services/processes.

---

# 5. Why Modular Monolith

Prospectra MVP does not have enough volume or organizational complexity to justify microservices.

A modular monolith gives us:

* simpler local development
* easier debugging
* fewer deployment problems
* lower cost
* easier transactions
* easier schema management
* simpler testing
* faster iteration

The code should still have clean module boundaries so that a component can later be extracted if a real requirement emerges.

# 9. Frontend Rules

The frontend must:

* call domain-level APIs
* validate user-facing input
* never contain provider-specific logic
* never contain secret API keys
* never directly call external providers that require server secrets
* never determine final qualification/score independently
* never bypass backend authorization

Frontend calculations may exist for purely presentational purposes, but backend remains authoritative.

```text

```


# 24. ICP Engine

The ICP Engine has two distinct responsibilities.

### Interpretation

Convert natural language into structured criteria.

### Validation

Ensure the generated criteria are:

* schema-valid
* supported
* internally coherent

Flow:

```text
User language
    ↓
AI Provider
    ↓
Structured ICP
    ↓
Schema validation
    ↓
Business-rule validation
    ↓
User confirmation
```

An unvalidated AI interpretation must not automatically start a search.

# 25. Search Orchestrator

The Search Orchestrator owns the lifecycle of a search.

It should answer:

```text
What stage is this search in?
What work is pending?
What work is completed?
What should run next?
What can run in parallel?
When can the next stage start?
What happens after failure?
Is the search complete?
```

It coordinates jobs but does not contain every provider-specific operation itself.

# 29. Job Processing

Job lifecycle:

```text
PENDING
   ↓
RUNNING
   ↓
SUCCEEDED
```

```text
RUNNING
   ↓
FAILED
   ↓
RETRY
   ↓

```


The exact payload contracts will be defined during implementation.

---

# 31. Job Idempotency

Every job handler must be safe to retry.

Examples:

* repeated normalization should not create duplicate businesses
* repeated website analysis should not create uncontrolled duplicate records
* repeated qualification should update/version the result appropriately
* repeated export request should not corrupt existing exports

Assume jobs are **at-least-once**, not exactly-once.

---

# 32. Job Retry Strategy

Retry temporary failures.

Examples:

```text
timeout
temporary network failure
provider 429
temporary provider outage
```

Do not blindly retry:

```text
invalid input
invalid URL
blocked private destination
unsupported operation
permanent provider error
```

Retry policy should include bounded attempts and delayed retry timing.

---

# 33. Job Failure Isolation

A failed candidate should not automatically fail the entire search.

Example:

```text
Candidate A → success
Candidate B → website failed
Candidate C → success
Candidate D → AI unavailable
```

The search can still complete with partial candidate-level states.

---

# 34. Parallel Processing

Independent enrichment operations may run concurrently.

Example:

```text
Candidate
   │
   ├── Website verification
   ├── Contact extraction
   └── Search enrichment
             │

```

Concurrency must remain bounded.



```text

→ ICP state/logic

Search module
→ Search lifecycle

Business module
→ Business data

Evidence module
→ Evidence

Qualification module
→ Qualification

Scoring module
→ Score

Prospect module
→ Sales state
```

Other modules should interact through defined interfaces rather than manipulating another module's internal structures casually.

---

# 68. Transaction Boundary Principle

Use database transactions for small atomic domain operations.

Examples:

```text
create prospect
update prospect state
record activity
save suppression
persist qualification result
```

Do not keep database transactions open while waiting for external providers or LLMs.

External calls happen outside long-running DB transactions.

---

# 69. External Call Boundary

Bad:

```text
open DB transaction
  ↓
call website
  ↓
wait
  ↓
call AI
  ↓
wait
  ↓
commit
```

Good:

```text
read state
 ↓
external call
 ↓
validate result
 ↓
short DB transaction
 ↓
persist
```

This avoids locking database resources during slow network operations.

---

# 70. Caching Philosophy

For MVP, do not build a large distributed caching architecture.

Prefer:

* persisted canonical data
* persisted evidence
* idempotent analysis results
* appropriate reuse of existing stored information

Caching should only be added when a demonstrated performance/cost problem exists.

---

# 71. Data Freshness

Business information changes.

Therefore source/evidence records should include timestamps.

Conceptually:

```text
observed_at
retrieved_at
updated_at
```

Scoring can consider freshness.

The system should avoid presenting stale information as if it were newly verified.

---

# 72. Result Snapshotting

A search result should preserve the result state at the time of the search.

Therefore:

```text
SearchResult
 ├── rank
 ├── score_snapshot
 └── qualification_snapshot
```

Later score changes should not unexpectedly rewrite historical search output.

---

# 73. Versioned Decisions

The following should be versioned:

```text
ICP
qualification rules
scoring rules
AI model
AI prompt
AI schema
```

This is necessary for reproducibility.

---

# 74. Cost-Aware Execution Strategy

The workflow should be a funnel.

```text
                 HIGH VOLUME
                     │
                Discovery
                     ↓
                Normalize
                     ↓
                Deduplicate
                     ↓
                Cheap Filter
                     ↓
                Verification
                     ↓
                Enrichment
                     ↓
                 AI Analysis
                     ↓
                Qualification
                     ↓
                  Scoring
                     ↓
              HUMAN SELECTION
                     ↓
               Deep Research
                 LOW VOLUME
```

This is one of the most important architectural characteristics of Prospectra.

---

# 75. Core Design Principle: Progressive Intelligence

Prospectra should progressively increase intelligence and cost.

```text
Layer 1 — Raw discovery
Layer 2 — Data quality
Layer 3 — Deterministic signals
Layer 4 — Semantic AI interpretation
Layer 5 — Qualification
Layer 6 — Explainable prioritization
Layer 7 — Human-directed research
```

Do not jump directly to the most expensive layer.

---

# 76. API → Application → Domain → Infrastructure

The logical dependency direction should be:

```text
API
 ↓
Application services
 ↓
Domain logic
 ↓
Interfaces
 ↓
Infrastructure adapters
```

Infrastructure should implement the interfaces required by the application.

This helps keep business logic provider-independent.
